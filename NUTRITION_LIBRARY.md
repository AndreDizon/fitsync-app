The nutrition library contains the approved 100 foods common in Filipino meals, retaining their Tagalog names, across seven primary categories. Each has six Filipino dish, dessert or home-style serving examples (600 total), also listed in `PHILIPPINE_FOOD_CANDIDATES.md`. Run `npm run seed:foods` to regenerate `backend/data/foods.json`. Frontend development and builds also regenerate the seed. Numbered pages display up to 24 foods each; searches and filters query all 100 records and reset to page one. Search includes Tagalog aliases and dish examples.

`scripts/philippine-food-catalog.json` defines the 100 identities, original USDA identifiers, preparation states, Tagalog aliases, dish examples and reference notes. `scripts/philippine-foods.mjs` adds browsing metadata and original source portions. Ingredient-allergen exclusions apply to the reference food, not a complete example dish. Protein foods is a browsing group, not a quantified high-protein claim; legumes and soy overlap it. The former curated/expansion scripts are retained as historical metadata and are no longer used by the seed.

To rebuild the checked-in source subset from the original USDA archive, extract its CSV files and run `node scripts/import-food-source.mjs <extracted-directory>`, then `npm run seed:foods`. The importer preserves original source descriptions, numeric nutrient values and household gram weights, including older source rows. Normal builds do not access the network. Where no source household measure is available, the interface uses edible grams and the 100 g reference. All 100 active foods have individual, locally authored SVG illustrations from `scripts/food-artwork.mjs`; the generated SVG is bundled in the public food seed, so artwork does not require external image downloads and remains available with the loaded app offline.

Cards, group filters and food details use consistent labeled group colors. Food details prioritize the reference state, edible-portion calculator and nutrient summary, followed by six dish ideas. Full nutrients, preparation guidance, dietary information, benefits and exact source notes remain available in closed-by-default disclosures. Color supplements the written group labels rather than replacing them.

Nutrition and household measure weights come from USDA FoodData Central SR Legacy (April 2018), published April 2019. `backend/data/foods-source.json` preserves the selected source rows, archive URL and archive SHA-256. FitSync descriptions, preparation notes, qualitative budget labels and dish examples are separate editorial metadata. Preparation times are planning estimates. Some USDA fish/shellfish references cover different species from those sold under local names; these limits are stated in the description and exact source. For example, the pompano reference is Florida pompano and the alimango reference is blue crab, not a specific laboratory analysis of local golden pompano or mud crab. Never infer complete-dish nutrients from an ingredient's six serving examples. The meal scanner receives exact reference descriptions and notes alongside IDs and food states.

Existing saved plans and playlists remain readable through `backend/data/foods-legacy.json` and `shared/food-catalog.ts`. Original IDs are reused only when their USDA record and nutrient values are unchanged. Removed foods stay available for historical calculations, not new library browsing or formulation. Raw foods explicitly requiring cooking are excluded from automatic formulation.

Before using new foods on a deployed database, run `backend/migrations/20261128_philippine_food_catalog.sql` after the earlier plan migrations. It adds public catalog identifiers only, preserves original identifiers and does not change any user records. Regenerate it with `node scripts/seed-playlist-catalog.mjs` if the curated IDs change. Do not rerun the initial schema migration as a substitute for this addition.

Validation: `node scripts/validate-foods.mjs` checks original nutrient/portion parity and dietary flags; `node scripts/validate-philippine-foods.mjs` checks all 100 approved names, six distinct examples each, stable historical nutrients, dish search and the idempotent catalog migration in an isolated PostgreSQL database. These checks do not modify hosted Supabase.

Every nutrient value uses a 100 g edible-weight basis, scaled to the chosen gram-backed serving. Raw/dry, cooked and ready-to-eat states remain distinct. Missing nutrients remain null. Generic records do not establish product-specific allergy or halal suitability.

Nutrition mode has a reference-only food library. Its default content never changes based on onboarding. Manual search and classification filters browse all 100 records; aliases include kanin, munggo, tokwa and saging. Food details include default source portions and an informational gram calculator. Users build their own account-backed menus inside Playlist, where portions and meal times are stored.

Seeding also writes `/offline/foods.json` and a content-hashed `/offline/food-manifest.json`. The existing service worker saves this public catalog in its own versioned food cache when Nutrition opens. Its ready note appears only after saving; failed downloads offer retry, and an offline visit can confirm the saved copy. Food saving does not trigger the exercise media download. SVG food artwork is bundled and has no external image requests. The service worker never caches authenticated HTML, account data, API sessions or navigation pages. Opening the full app from a closed browser while offline is not supported by either library cache.

Manual account menus and offline synchronization are documented in PLAYLISTS_SETUP.md. Automatic meal generation remains separate; the library does not generate personal calorie targets or prescriptions.
